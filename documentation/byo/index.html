Prerequisites

Before you start, make sure you have your Sageion API key and your app details ready.

Client Integration

Sageion exposes two methods on `window.sageion_os`: `setUp()` and `initialize()`. Everything else — sockets, DOM, auth, lifecycle, teardown — is handled internally.

Code Example

await window.sageion_os.setUp(
  "your_app_id",
  "YOUR_API_KEY",
  "US",
  "sageion-chat-root"
);

Backend Integration

Your backend must expose endpoints to authenticate users and return a token.

AI Agent Overview

The Sageion AI Agent turns your existing backend APIs into deterministic, multi-step workflows with auto-generated UI screens. It runs on top of any Restaurant CRM — Petpooja, Posist, Rista, or a custom stack — and is designed from the ground up for enterprise deployments supporting 60,000 base users and 10,000 power users across 70,000+ restaurants.

What is an agent

An AI Agent is a named skill your app exposes to end users — for example "Check order status" or "Book a table". Each agent is wired to either a single API config or a full API chain. When a user triggers the agent in chat, the runtime classifies the intent, picks the matching API or chain, renders the required input fields as a UI screen, executes the API deterministically, and renders the response using the template you designed.

Tenant vs App Scope

Sageion is built around a two-tier resource model. Understanding it is the key to understanding why the platform scales cleanly to 70,000 restaurants and why multi-admin works without chaos.

The two tiers

TierLives atShared byEditable by
TenantThe root account (e.g. your Restaurant CRM)Every app on the accountTenant admins only
AppA single app (e.g. one restaurant or franchise)That app onlyApp developers and managers on that app

The opt-in attachment model

Tenant-scoped resources are NOT visible to apps by default. An app must explicitly attach each resource it wants to use. This is the single most important design decision in the platform, because it makes tenant-wide infrastructure safe to share without giving every app blanket access.

Fail-hard guards

If a tenant admin tries to delete or modify a resource that is still attached to an app, the platform refuses the action and names the blocking apps. Nothing is silently broken.

App overrides

If an app needs to deviate from the tenant default — different pricing, different auth, a custom chain — the app developer creates an app-scoped version of that resource. The app-scoped version shadows the tenant one for that app only.

Why this scales to 70,000 restaurants

The tenant tier is where 90% of the work happens. The tenant admin defines the golden API configs, golden auth server, and golden workflows once. Each of the ~70,000 restaurants is one app on that tenant — it inherits everything by attaching, without duplicating infrastructure.

Multi-Admin & RBAC

Sageion supports multiple administrative users per tenant with role-based access control. This is what allows a Restaurant CRM with 70,000 downstream restaurants to delegate safely.

Roles

RoleScopeCan do
Super AdminTenant-wideManage tenant settings, invite admins, publish shared resources

Inviting a support user

From Global Level Settings, the admin selects the role and scope (tenant or specific app). An invitation is sent with a signed link that expires in 7 days.

App-scoped admins

App developers and app managers are scoped to a specific app_name. They can only see resources, workflows, and metering for that app. Their blast radius is one restaurant.

API Chains

A Chain runs several API configs in sequence, with branching on response status codes. This is how a single agent handles multi-step workflows without writing a single line of code.
Here is a real-world example: a restaurant manager asks the AI Agent to "Check if we need to order rice and handle the approval." The runtime executes a 3-step chain:

Step 1: Check Inventory (Parent)

The chain hits the inventory endpoint to see if Basmati Rice is low.
curl -s -X GET http://api.yourcrm.com/inventory/rice \
  -H "Authorization: Bearer {{ token }}"

# Response (200 OK)
{
  "material_id": "rice",
  "name": "Basmati Rice",
  "current_qty": 3,
  "unit": "kg",
  "low_threshold": 4
}

Step 2: Create Purchase Order (Child)

Because the quantity is low, the chain automatically triggers the next API. Notice how it takes the {{ material_id }} from Step 1 and injects it directly into the payload for Step 2.
curl -s -X POST http://api.yourcrm.com/purchase-orders \
  -H "Authorization: Bearer {{ token }}" \
  -H "Content-Type: application/json" \
  -d '{
    "supplier": "FreshMeat", 
    "material_id": "{{ response_data.material_id }}", 
    "qty": 5, 
    "unit": "kg"
  }'

# Response (201 Created)
{
  "po_id": "PO-BDE7BB",
  "status": "pending_supplier"
}

Step 3: Approve Purchase Order (Grandchild)

For critical actions, the chain can pause for human-in-the-loop approval. Once approved, it takes the {{ po_id }} from Step 2, injects it into the URL, and finalizes the order.
curl -s -X PATCH http://api.yourcrm.com/purchase-orders/{{ response_data.po_id }}/approve \
  -H "Authorization: Bearer {{ token }}" \
  -H "Content-Type: application/json" \
  -d '{
    "approved": true
  }'

# Response (200 OK)
{
  "success": true,
  "po_id": "PO-BDE7BB",
  "status": "approved",
  "inventory_updated": true
}

No Code Required

This entire 3-step workflow — including payload transformation, branch logic, and auth headers — is configured visually in the CanvasView editor. The LLM only detects the initial intent ("Order rice"). The runtime handles the rest deterministically.

Visual Response Designer

The Visual Response Designer is where you tell the AI Agent what to render after an API call. Instead of returning raw JSON or a chat message, you design a structured screen — a card, a table, an approval dialog, a form — from the API's actual response shape.

What is it?

It is a no-code editor that takes the sample response from an API Config and lets you map each field into a UI component. The result is rendered by the same deterministic engine used across the platform — no LLM involvement.

Getting started

Open the Preview Tester from any API Config, paste a sample response, and start designing the layout.

Best practices

  • Use a real sample response — not synthetic data.
  • Design the error states (400, 404, 409) before shipping the happy path.
  • Keep text templates short.

Whitelabel & Billing

The platform is designed to be invisible to the end restaurant. Every domain, every screen, and every metered event can be attributed to a specific app — which means the CRM vendor can bill each restaurant individually.

Whitelabel domains

A tenant can register custom domains that serve the AI Agent interface under the tenant's own brand.

Billing Granularity

Every execution the agent runs is stamped with app_name and user_identity. These two tags are the entire billing surface. A CRM vendor takes the metering export and produces a per-restaurant invoice directly.
