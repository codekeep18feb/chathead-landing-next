V2 Integration: Turn Your APIs into AI Agents

Sageion V2 is designed for products with their own backend and authentication. Keep your users in your database, keep your APIs as the source of truth, and use Sageion as a hollow wrapper to instantly give them autonomous AI capabilities.

Prerequisite

  1. Sign up / log in to your Sageion account.
  2. Create a New App and select Version V2 during setup.
  3. Open the App Details page and note your: App Name, API Key, and Region (US or IN).

You can change these later

Bots, settings, and theme are all editable from the App Details page after creation. Pick whatever makes sense to start with.

Client Integration

Client Side Integration

Sageion exposes two methods on window.sageion_os: setUp() and initialize(). Everything else — sockets, DOM, auth lifecycle, teardown — is handled internally.

The API in one sentence

Call setUp() once per page load. Call initialize({ uid }) whenever the current user changes — logged in, logged out, or switched. That's the entire contract.

The four rules of a correct integration

  1. setUp() runs once, awaited, before any initialize().
  2. initialize() is called from exactly one place in your app.
  3. initialize() is gated on your auth state having settled — not on the user being non-null.
  4. initialize() receives the current user, once per change.
Follow these four rules and Sageion handles every transition — login, logout, user-switch, token refresh — without a page reload. The SDK is idempotent: calling initialize() twice with the same payload is a safe no-op, so you never need to add re-render guards.

1. Load the scripts

Locate your app's root HTML shell (usually index.html or a base layout template) and insert the following scripts. Socket.IO must load before the Sageion bundle.
<script src="https://cdn.socket.io/4.1.2/socket.io.min.js"></script>
<script src="https://magicchat-core.github.io/prod-ssc-client-cdns/bundle.js"></script>

The SDK is a global, not an npm package

Loading the bundle exposes window.sageion_os. There is no npm install, no import statement, and no build-time integration.

Optional: custom mount point

By default, the chat bubble floats in the bottom-right corner. To anchor it inside a specific container, add an empty element to your markup and pass its id as the fourth argument to setUp():
<div id="sageion-chat-root"></div>

2. Pick your framework

Pick your framework from the tabs below. Inside each you will find three integration styles — choose the one that matches your app's structure.
<script>
  (async () => {
    try {
      await window.sageion_os.setUp("your_app_id", "YOUR_API_KEY", "US");

      const token = localStorage.getItem("token");
      let payload = {};

      if (token) {
        const res = await fetch("https://api.yourbackend.com/auth/profile", {
          headers: { Authorization: `Bearer ${token}` }
        });
        if (res.ok) {
          const user = await res.json();
          payload = { uid: user.id.toString() };
        } else {
          localStorage.removeItem("token");
        }
      }
      await window.sageion_os.initialize(payload);
    } catch (err) {
      console.error("[Sageion] bootstrap failed:", err);
    }
  })();
</script>

Reflecting login & logout at runtime

// wherever your app knows the user changed:
function onAuthChanged(user, loading) {
  if (loading) return;
  window.sageion_os
    .initialize(user ? { uid: String(user.id) } : {})
    .catch(err => console.error("[Sageion] sync failed:", err));
}

Backend Integration

Sageion does not own your user identities. Your product remains the source of truth — users sign up and log in against your own backend, and Sageion is told about them via a small onboarding call. Everything Sageion needs from your backend is exposed through a single SDK, @sageion/node.

The Sageion SDK

Sageion ships an official SDK for Node.js. It is framework-agnostic and has zero external dependencies. The SDK handles the pieces you would otherwise have to write by hand: hybrid RSA/AES token encryption, the onboarding HTTP call, correlation-id extraction, and webhook dispatch.
npm install @sageion/node
The SDK reads all configuration from your .env file at import time. Set the following variables before your server starts.
# Your Sageion App Credentials (from Admin Panel → App Details)
SAGEION_APP_ID="APP-mw5bc7im-h5xvwm"
SAGEION_REST_API_KEY="your_rest_api_key"
SAGEION_CLIENT_SECRET="your_client_secret"
SAGEION_APP_NAME="your_app_name"   # Used as the client_id for /client-user-token
SAGEION_REGION="us"                 # Defaults to 'us'

# The public key used for token encryption (provide ONE of these)
SAGEION_PUBLIC_KEY_PATH="/etc/sageion/sageion-public.pem"
# OR
# SAGEION_PUBLIC_KEY_PEM="-----BEGIN PUBLIC KEY-----\n...\n-----END PUBLIC KEY-----"

The three core functions

Step 1 — Onboarding a user

The moment your signup handler commits the user to your own DB, call onboardUser(). The call is fire-and-forget: your signup succeeds even if Sageion is temporarily unreachable.
// routes/auth.js
const { onboardUser } = require('@sageion/node');

router.post('/register', [...validators], async (req, res) => {
  const { email, password, full_name } = req.body;

  const hashed = await hashPassword(password);
  const result = await pool.query(
    'INSERT INTO users (email, password_hash, full_name) VALUES ($1, $2, $3) RETURNING id, email, full_name, role',
    [email, hashed, full_name]
  );
  const user = result.rows[0];

  try {
    await onboardUser(user.id.toString(), process.env.SAGEION_APP_ID, {
      email: user.email,
      full_name: user.full_name,
      image: "https://img.magnific.com/free-vector/blue-circle-with-white-user_78370-4707.jpg",
    });
  } catch (onboardErr) {
    console.error('[Sageion] onboarding error:', onboardErr.message);
  }

  const token = generateToken(user.id, user.email, user.role);
  res.status(201).json({ token, user });
});

Step 2 — Node Execution Types

🚀 Turn your existing APIs into AI Agents

You already have a powerful backend. Your APIs do the heavy lifting, but right now, they're just sitting there waiting for a frontend to click a button. Sageion unlocks them.
Sageion turns your existing APIs into autonomous AI Agents. Because the AI must call your API to get an answer, it never hallucinates—it gets the absolute truth directly from your own backend. We don't store your business data; Sageion is a hollow wrapper that simply fills the gap between 'user intent' and 'your API'.
It gives you instant AI capabilities to build anything whatsoever, while you manage most of it through an easy UI admin panel.

📖 The Story: The Assistant and The Ticket

To make this happen, imagine the Sageion AI Agent is a new Executive Assistant. A user gives the Assistant a task (a Chain): "Find the customer, check their order, and refund them."
To finish this, the Assistant has to run errands to your backend APIs (the Nodes). Depending on how your API is built, the Assistant will experience one of three scenarios:
ScenarioNode TypeWhat HappensSetup Required
InstantSync NodeThe Assistant asks for data, and your API replies immediately in the HTTP response. The Assistant checks it off and moves on.None
BackgroundAsync NodeYour API says: "I'll put this in a queue. Here is a Ticket (Correlation ID). I'll call you when it's done." The Assistant moves to the next task while you work.Webhook
Human PauseManual NodeYour API says: "I need a Manager to approve this. Here is a Ticket. I'll call you back when the human clicks Approve." The Assistant waits.Webhook

🏆 The Golden Rule

For Async and Manual Nodes, Sageion pauses the Chain and waits. It is your backend's job to hold onto that Ticket using getCorrelationId(req), and use dispatchWebhookAsync() to call the Assistant back once the work is actually finished.

No special SDK code required

Use this for APIs that compute and return the final result within a few seconds (e.g., fetching a menu, checking inventory). Sageion reads the final result directly from the HTTP response body.
router.post('/bookings', async (req, res) => {
  // Do the work immediately
  const booking = await createBooking(req.user.userId, req.body);
  
  // Return the result to Sageion right away
  res.status(201).json({ success: true, booking_id: booking.id });
});

Step 3 — Authenticated APIs & the AI Agent

Required only if your APIs are protected by JWT

If the endpoints you expose to Sageion require a Bearer token (JWT), the AI Agent cannot call them as a generic client. You must implement a `/auth/client-user-token` endpoint so Sageion can securely act on behalf of a specific user.

AI Agent Overview

The Sageion AI Agent turns your existing backend APIs into deterministic, multi-step workflows with auto-generated UI screens. It runs on top of any Restaurant CRM — Petpooja, Posist, Rista, or a custom stack — and is designed from the ground up for enterprise deployments supporting 60,000 base users and 10,000 power users across 70,000+ restaurants.

What is an agent

An AI Agent is a named skill your app exposes to end users — for example "Check order status" or "Book a table". Each agent is wired to either a single API config or a full API chain. When a user triggers the agent in chat, the runtime classifies the intent, picks the matching API or chain, renders the required input fields as a UI screen, executes the API deterministically, and renders the response using the template you designed.

The three layers

PresentationRenders forms, tables, approval cards, and text templates from the API's declared response shape.Developer via Visual Response Designer
OrchestrationMaps intent → API/Chain, handles field extraction, branch logic, async pauses, and human-in-the-loop stops.Developer via Skill Workflow
IntegrationHandles auth (Bearer, API key, OAuth2, JWT), request signing, webhook callbacks, and outbound validation.Developer via API Config & Auth Integration

Tenant vs App Scope

Sageion is built around a two-tier resource model. Understanding it is the key to understanding why the platform scales cleanly to 70,000 restaurants and why multi-admin works without chaos.

The two tiers

TierLives atShared byEditable by
TenantThe root account (e.g. your Restaurant CRM)Every app on the accountTenant admins only
AppA single app (e.g. one restaurant or franchise)That app onlyApp developers and managers on that app

The opt-in attachment model

Tenant-scoped resources are NOT visible to apps by default. An app must explicitly attach each resource it wants to use. This is the single most important design decision in the platform, because it makes tenant-wide infrastructure safe to share without giving every app blanket access.

Fail-hard guards

If a tenant admin tries to delete or modify a resource that is still attached to an app, the platform refuses the action and names the blocking apps. Nothing is silently broken.

App overrides

If an app needs to deviate from the tenant default — different pricing, different auth, a custom chain — the app developer creates an app-scoped version of that resource. The app-scoped version shadows the tenant one for that app only.

Why this scales to 70,000 restaurants

The tenant tier is where 90% of the work happens. The tenant admin defines the golden API configs, golden auth server, and golden workflows once. Each of the ~70,000 restaurants is one app on that tenant — it inherits everything by attaching, without duplicating infrastructure.

Multi-Admin & RBAC

Sageion supports multiple administrative users per tenant with role-based access control. This is what allows a Restaurant CRM with 70,000 downstream restaurants to delegate safely.

Inviting a support user

From Global Level Settings, the admin selects the role and scope (tenant or specific app). An invitation is sent with a signed link that expires in 7 days.

App-scoped admins

App developers and app managers are scoped to a specific app_name. They can only see resources, workflows, and metering for that app. Their blast radius is one restaurant.

API Chains

A Chain runs several API configs in sequence, with branching on response status codes. This is how a single agent handles multi-step workflows without writing a single line of code.
Here is a real-world example: a restaurant manager asks the AI Agent to "Check if we need to order rice and handle the approval." The runtime executes a 3-step chain:

Step 1: Check Inventory (Parent)

The chain hits the inventory endpoint to see if Basmati Rice is low.
curl -s -X GET http://api.yourcrm.com/inventory/rice \
  -H "Authorization: Bearer {{ token }}"

# Response (200 OK)
{
  "material_id": "rice",
  "name": "Basmati Rice",
  "current_qty": 3,
  "unit": "kg",
  "low_threshold": 4
}

Step 2: Create Purchase Order (Child)

Because the quantity is low, the chain automatically triggers the next API. Notice how it takes the {{ material_id }} from Step 1 and injects it directly into the payload for Step 2.
curl -s -X POST http://api.yourcrm.com/purchase-orders \
  -H "Authorization: Bearer {{ token }}" \
  -H "Content-Type: application/json" \
  -d '{
    "supplier": "FreshMeat", 
    "material_id": "{{ response_data.material_id }}", 
    "qty": 5, 
    "unit": "kg"
  }'

# Response (201 Created)
{
  "po_id": "PO-BDE7BB",
  "status": "pending_supplier"
}

Step 3: Approve Purchase Order (Grandchild)

For critical actions, the chain can pause for human-in-the-loop approval. Once approved, it takes the {{ po_id }} from Step 2, injects it into the URL, and finalizes the order.
curl -s -X PATCH http://api.yourcrm.com/purchase-orders/{{ response_data.po_id }}/approve \
  -H "Authorization: Bearer {{ token }}" \
  -H "Content-Type: application/json" \
  -d '{
    "approved": true
  }'

# Response (200 OK)
{
  "success": true,
  "po_id": "PO-BDE7BB",
  "status": "approved",
  "inventory_updated": true
}

No Code Required

This entire 3-step workflow — including payload transformation, branch logic, and auth headers — is configured visually in the CanvasView editor. The LLM only detects the initial intent ("Order rice"). The runtime handles the rest deterministically.

Visual Response Designer

The Visual Response Designer is where you tell the AI Agent what to render after an API call. Instead of returning raw JSON or a chat message, you design a structured screen — a card, a table, an approval dialog, a form — from the API's actual response shape.

What is it?

It is a no-code editor that takes the sample response from an API Config and lets you map each field into a UI component. The result is rendered by the same deterministic engine used across the platform — no LLM involvement.

Getting started

Open the Preview Tester from any API Config, paste a sample response, and start designing the layout.

Best practices

  • Use a real sample response — not synthetic data.
  • Design the error states (400, 404, 409) before shipping the happy path.
  • Keep text templates short.

Whitelabel & Billing

The platform is designed to be invisible to the end restaurant. Every domain, every screen, and every metered event can be attributed to a specific app — which means the CRM vendor can bill each restaurant individually.

Whitelabel domains

A tenant can register custom domains that serve the AI Agent interface under the tenant's own brand.

Billing Granularity

Every execution the agent runs is stamped with app_name and user_identity. These two tags are the entire billing surface. A CRM vendor takes the metering export and produces a per-restaurant invoice directly.
